# @puntjes/sdk

The official TypeScript client for the [Puntjes](https://puntjes.app) loyalty API. It runs on Node 20 or later and
ships as an ES module with its own types.

```bash
npm install @puntjes/sdk
```

Use it on a server only. The client secret gives full access to your shop's API, so it must never reach a browser.

## Quick start

Create your API credentials in the Puntjes admin portal. The secret is shown once.

```ts
import { createPuntjes, idempotencyKey } from '@puntjes/sdk';

const puntjes = createPuntjes({
  clientId: process.env.PUNTJES_CLIENT_ID!,
  clientSecret: process.env.PUNTJES_CLIENT_SECRET!,
});

// A customer scans their card at the till.
const { data: customer } = await puntjes.lookupCustomer({ query: { identifier: scannedCard } });
console.log(customer.data.wallet_balance);

// Record the purchase. Amounts are in cents.
const { data: transaction } = await puntjes.submitTransaction({
  body: { identifier: scannedCard, total_amount: 4200, idempotency_key: `order-${orderId}` },
});
console.log(transaction.data.points_earned);
```

`createPuntjes` returns a client generated from the Puntjes OpenAPI document, so it has every call the API has, with
the types of every request and answer. Each call takes `path`, `query` and `body` as the API names them and returns
`{ data, request, response }`. The API wraps each answer in its own `data` field, so the record is `data.data`.

`examples/quick-start.ts` is a complete script:
`npm run build && node examples/quick-start.ts <card number> [amount in cents]`, with `PUNTJES_CLIENT_ID`,
`PUNTJES_CLIENT_SECRET` and, for a local app, `PUNTJES_BASE_URL` set.

## Options

```ts
const puntjes = createPuntjes({
  clientId,
  clientSecret,
  baseUrl: 'https://puntjes.app', // with or without /api/v1
  maxRetries: 2,                  // 0 turns retries off
  retryBaseDelay: 500,            // milliseconds before the first retry, doubled for each next one
  timeout: 30_000,                // milliseconds per attempt
  tokenStore: myRedisStore,       // a TokenStore; memory by default
  fetch: myFetch,                 // a fetch for a proxy or a test; the global fetch by default
});
```

## What the SDK does for you

- **Authentication.** It asks for a `client_credentials` token on the first call, keeps it until 30 seconds before it
  expires, and asks once more when the API rejects it. Parallel calls share one request for a token. A `TokenStore`
  keeps each token under a key made from the host and the credentials, so one shared store (Redis, for example) can
  serve the clients of many shops without mixing their tokens. The key is the same one the .NET SDK uses.
- **Retries.** A GET, PUT, PATCH or DELETE, and a POST that carries an `idempotency_key`, is sent again after a network
  failure, a 5xx answer or `RATE_LIMITED`. It waits 0.5 s, then 1 s, or what `Retry-After` says. A POST without a key
  is never sent twice, so a purchase is never recorded twice. `PLAN_LIMIT_EXCEEDED` is never retried. An attempt that
  takes longer than `timeout` counts as a network failure. A failed token request is retried the same way.
- **Idempotency keys.** `idempotencyKey()` makes one. Send the same key again to repeat a call safely.

## Errors

Every error is a `PuntjesError`, with a subclass per kind:

| Error | When |
|---|---|
| `AuthenticationError` | 401: wrong credentials or a rejected token |
| `ForbiddenError` | 403 |
| `NotFoundError` | 404 |
| `ConflictError` | 409 |
| `ValidationError` | 422 `VALIDATION_ERROR`; `errorsFor('field')` gives the messages |
| `RateLimitError` | 429 `RATE_LIMITED`; `retryAfter` says how many milliseconds to wait |
| `PlanLimitExceededError` | 429 `PLAN_LIMIT_EXCEEDED`: the shop's plan is used up |
| `ServerError` | 5xx |
| `TransportError` | No answer from the API, or an answer that is not from the API |

A 422 for a business rule, such as `INSUFFICIENT_BALANCE`, is a plain `PuntjesError`.

```ts
import { ErrorCode, PuntjesError } from '@puntjes/sdk';

try {
  await puntjes.redeemReward({ body });
} catch (error) {
  if (error instanceof PuntjesError && error.code === ErrorCode.InsufficientBalance) {
    console.log(`Not enough points. Request ${error.requestId}`);
  } else {
    throw error;
  }
}
```

`code` is null for a code that is newer than your SDK; `rawCode` always holds the code as the API sent it.

## Pages

```ts
import { paginate, type ProductData } from '@puntjes/sdk';

for await (const product of paginate<ProductData>(async (page) => (await puntjes.listProducts({ query: { page } })).data.data)) {
  console.log(product.name);
}
```

## How this package is made

The code under `src/generated` is generated by [hey-api](https://heyapi.dev) from `spec/api.json`. Never edit it by
hand: CI regenerates it and fails on any difference. A bump of `@hey-api/openapi-ts` turns that check red until the
code is regenerated in the same PR, and that is the point of the check.

- `npm run generate` regenerates it: hey-api, then `tools/codegen.ts` for the `ErrorCode` list. hey-api is pinned to
  an exact version, and TypeScript is pinned to 5 beside it, because hey-api fails under TypeScript 7.
- When Puntjes publishes a new API spec, `.github/workflows/regenerate.yml` opens a PR with the new code. A minor or
  patch spec merges itself when CI is green; a major one waits for a person.
- `.github/workflows/release.yml` runs release-please. Its release PR merges itself when CI is green, and the tag
  publishes the package to npm with provenance.

### Releases and npm trusted publishing

The publish job has no stored npm token. npm trades the job's GitHub token for a one-time credential and adds the
provenance statement itself. npm can attach a trusted publisher only to a package that exists, so the first version
goes by hand, once:

1. The `1.0.0` release PR merges and release-please tags `v1.0.0`. The publish job fails and points here.
2. An owner of the `puntjes` npm organisation checks out `v1.0.0` and runs `npm ci && npm run build &&
   npm publish --access public`.
3. Within two days, on npmjs.com, open the package's **Settings**, then **Trusted Publisher**, choose GitHub Actions,
   and enter organisation `PuntjesApp`, repository `puntjes-typescript`, workflow `release.yml`, no environment.
   Then set **Publishing access** to require two-factor authentication and disallow tokens.
4. Re-run the failed publish job. It sees that `1.0.0` is on npm and passes. Every later release publishes by itself.
